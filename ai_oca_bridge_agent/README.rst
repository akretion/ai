Bring your own agent
--------------------

This module connects Odoo Discuss to an **external AI agent runtime**
and gives that runtime a safe way to work on Odoo data as the user who
is chatting. It does not run a model itself and does not embed a prompt:
it owns the transport, the identity and the policy, and the agent lives
outside Odoo.

The contract is four plain HTTP endpoints, so the runtime can be
anything that speaks them: an agent framework, an automation platform
(n8n), or a service of your own. **Hermes Agent is the reference
implementation** and the one Akretion runs in production; a reference
responder is published separately (Hermes Agent plus a small HTTP
adapter) so the contract is readable as running code rather than as a
specification only.

Because the agent runs elsewhere, it can do things an in-Odoo assistant
cannot: use its own skills and files, browse, call other systems, run on
a model of your choice, and be redeployed without an Odoo upgrade. What
stays in Odoo is the part that must not be delegated: who may talk to
the assistant, what it may read or create, and the audit trail.

Real-time or polling, pick one
------------------------------

The module exposes two transports for the same conversation:

- **Push (recommended)**: Odoo signs an event with an HMAC secret and
  posts it to the responder the moment a message is committed. Latency
  is one HTTP call, and no Odoo worker is ever held waiting.
- **Polling (fallback)**: the responder calls ``/ai_agent/poll`` and
  *claims* the pending messages atomically. Works through any firewall,
  no inbound route needed on the Odoo side, but costs one request per
  interval per tenant.

Both transports share one envelope, so a responder can switch from one
to the other without touching the Odoo configuration beyond a checkbox.

Multi-tenant by construction
----------------------------

One responder installation can serve many Odoo databases:

- every database owns a stable ``tenant_key`` (an
  ``ir.config_parameter``, independent from ``database.uuid``) and an
  ``environment`` (``prod``/``staging``/``dev``);
- the session key is ``odoo:<tenant_key>:<environment>:user_<id>``, so a
  staging database restored from production never continues the
  production conversation;
- messages are claimed with ``FOR UPDATE SKIP LOCKED``: any number of
  responder workers and Odoo HTTP workers can run concurrently without a
  duplicate delivery;
- replies are idempotent (``delivery_id``), and a reply closes exactly
  the message it answers, not every message of the channel.

Who may talk to the assistant
-----------------------------

Access is a group (``Use the AI assistant``), configurable per agent.
System administrators always keep access so a fresh install stays
configurable. Someone outside the allowed groups who addresses the
assistant receives a configurable standard answer, posted at most once
per cooldown to avoid flooding the channel.

Two capability tiers per user
-----------------------------

Not every Odoo user wants to hand an API key to the assistant:

- a user **with** an Odoo API key is announced to the responder as
  ``full`` tier and the responder may call Odoo on their behalf, with
  their own access rights;
- a user **without** a key is announced as ``basic`` tier: generic
  assistant capabilities only, no Odoo data access.

The module only publishes the fact (``capabilities`` in the envelope)
and the policy stays on the responder side.
``require_api_key_for_tools`` decides whether a key is mandatory before
announcing ``odoo_rpc``.

Read and create under the user's own rights
-------------------------------------------

A connected user can let the assistant query Odoo. The default policy
follows the API key: read methods on any model that user may read, plus
``create`` (see ``USAGE.md``), never ``write`` or ``unlink`` unless
explicitly granted. Two optional restrictions exist for customers who
want the assistant weaker than its users: an explicit grant list, and a
deny list of models that must not be quoted into a channel other people
read.

What this module deliberately does not do
-----------------------------------------

The module is a transport, published under AGPL-3 in the OCA ``ai``
repository. It contains no prompt, no skill, no model choice, no
tenant-to-customer mapping, no quota and no escalation backend: all of
that is product logic and lives in the responder process, which talks to
Odoo only through the documented HTTP envelope. See ``CONTEXT.md`` for
the boundary and the extension points to use from your own (AGPL) child
modules.

Use Cases / Context
===================

Why This Module?
----------------

The AI revolution is changing how users interact with software. Odoo
users should be able to ask questions, get help, and automate tasks
using natural language — directly inside the interface they already use
daily.

Architecture Rationale
----------------------

**Two transports, one envelope**

Polling was the original design: it works behind firewalls and needs no
inbound route on the Odoo side. It stays as the **fallback**, but it
does not scale to many tenants (one request per interval per tenant, a
delayed answer, and a agent that has to hold the conversation state
between two polls).

The recommended transport is **outbound push**: Odoo signs the event and
posts it as soon as the transaction is committed (``cr.postcommit``), so
the agent never sees a message the database could still roll back. A
one-minute cron pushes whatever the post-commit hook could not send,
which makes a agent restart or a network glitch invisible to the user.

Both transports carry the same JSON envelope (see ``USAGE.md``), so the
agent only has to implement one parser.

**Stateless agent, persistent session per user**

The agent keeps **no** conversation state in Odoo: it authenticates with
a tenant key, reads the session key from the envelope, and answers with
a ``delivery_id``. The Hermes session itself is persistent
(``session_scope``: per user by default, per channel optionally), which
is what gives the assistant a memory across messages without storing a
transcript in Odoo.

**Atomic claiming**

``/ai_agent/poll`` claims messages with a single
``UPDATE ... FOR UPDATE SKIP LOCKED ... RETURNING``. This is what makes
several agent workers and several Odoo HTTP workers safe together, and
it removes the previous per-agent one-second throttle that capped every
tenant of a database.

**Standalone agent**

``scripts/agent_gateway_example.py`` polls in echo mode or with a Hermes
AIAgent. ``scripts/ai_agent_push_server.py`` is the reference push
receiver: it verifies the HMAC signature, answers, and is the place to
plug the agent call. Neither needs to run inside Odoo's Python
environment.

**Extension points**

The module is intentionally minimal. Child modules can extend, without
forking:

- ``ai.bridge.agent._is_user_allowed(user)`` — who may talk to the
  assistant;
- ``ai.bridge.agent._get_capabilities(message)`` — what the agent may do
  for that user (``full``/``basic``, ``odoo_rpc``, tool list);
- ``ai.bridge.agent._build_event_payload(message)`` — enrich the
  envelope with business context;
- ``ai.bridge.agent._get_session_key(user, channel)`` — session
  granularity;
- ``ai.bridge.agent.message._get_history(limit)`` — what the assistant
  sees of the conversation;
- ``discuss.channel._should_queue_for_agent(message, agent)`` — routing
  rules;
- ``ai_agent_webhook._action_escalate(agent, data)`` — escalation
  backend.

**The AGPL boundary (read this before adding private logic)**

This module is AGPL-3 and published at OCA. A child Odoo module that
inherits it is a derivative work: it must stay AGPL, and if you serve it
over the network the AGPL asks you to offer its source to the users. So
the private value of the product must **not** live in an Odoo module:

- keep in Odoo only the transport, the traceability and the coarse
  access policy that you are happy to publish;
- keep prompts, skills, tool whitelists, model/provider choice, tenant
  registry, quotas, billing and routing intelligence in the **agent
  process**, which talks to Odoo over the documented HTTP envelope;
- if a private Odoo child module is really needed, accept that it is
  AGPL too (that is fine for internal, non-distributed deployments, but
  it is a conscious choice, not an accident).

**Escalation Concept**

The module includes a minimal escalation hook (``_action_escalate``) so
the AI can signal when human intervention is needed. The base module
does not implement any specific escalation backend — child modules can
override this hook to create tickets, notify teams, or route to another
Hermes instance.

Security Model
--------------

- Webhook tokens are auto-generated, rotatable with a grace period (the
  previous token stays valid for ``token_grace_minutes``), compared in
  constant time and never trusted from the URL alone: the recommended
  endpoints authenticate with an HMAC signature over
  ``<timestamp>.<body>``;
- AI users are regular Odoo users with limited permissions;
- the agent runs with its own credentials and, per user, with that
  user's API key when there is one;
- queue rows are protected by a multi-company rule and by an
  own-messages-only rule for non-managers;
- the Odoo side never executes code sent by the agent.

Recommended presets
-------------------

- **Single customer, behind a firewall**: push disabled, long poll 20 s,
  one agent worker. Nothing has to reach Odoo from outside.
- **Akretion-style shared Hermes**: push enabled over HTTPS, HMAC secret
  per tenant, ``environment`` set per database, one agent worker per
  tenant queue.
- **Pilot with power users only**: allowed groups = a dedicated group,
  API key required for tools, session scope per user.

Usage
=====

Configuration
-------------

1. Create the AI user: a regular Odoo user, member of no group of its
   own, linked to an ``ai.bridge`` with usage *Hermes* (this is what
   makes Discuss treat it as an assistant).
2. Go to *AI Bridge > Hermes > Agents* and create a agent: name, AI
   user, environment (``prod``/``staging``/``dev``) and the groups
   allowed to chat with it. System administrators always keep access.
3. Copy the **webhook token** for the polling transport, and the **HMAC
   secret** (``push_secret``) for the push transport. Both are shown to
   system administrators only.
4. Optional: restrict the agent to specific channels, otherwise every
   channel the AI user belongs to is monitored, and group channels
   answer only when the assistant is mentioned.

**Real-time push (recommended)**

In the *Realtime push* section, check **Push enabled** and set the agent
URL, e.g. ``https://responder.example.com/ai_agent/events``. Odoo then
posts every new message after the transaction commits, signed with:

::

   X-Hermes-Tenant:    <tenant_key>
   X-Hermes-Timestamp: <unix seconds>
   X-Hermes-Delivery:  <uuid>
   X-Hermes-Signature: sha256=<hmac_sha256(push_secret, "<timestamp>.<raw body>")>

A one-minute cron retries whatever the post-commit hook could not
deliver, so a agent restart does not lose a message. Leaving push
disabled keeps the polling transport in charge.

**Polling (fallback)**

.. code:: bash

   python scripts/agent_gateway_example.py \
       --odoo-url https://odoo.example.com \
       --webhook-token YOUR_TOKEN \
       --poll-interval 5

Add ``--use-agent --model ... --provider ...`` to answer with a Hermes
AIAgent instead of echo mode. Set **Long poll timeout** on the agent
(0-20 s) to hold the request until a message arrives instead of paying a
fixed interval.

**Reference push receiver**

.. code:: bash

   python scripts/ai_agent_push_server.py \
       --port 8770 \
       --odoo-url https://odoo.example.com \
       --tenant <tenant_key> \
       --secret <push_secret> \
       --mode echo

It verifies the signature, answers ``/ai_agent/reply`` with the same
HMAC scheme and is the place to plug the agent call (``build_answer``).

Access control
--------------

Users outside the allowed groups are answered with a standard message
(configurable per agent, *Access denied message*), posted at most once
per ``denial_cooldown_minutes`` per channel. Administrators are always
allowed.

Two capability tiers
--------------------

The envelope announces what the agent may do for the user:

- ``tier: "full"``, ``odoo_rpc: true`` — the user owns an Odoo API key,
  so the agent can call Odoo with that user's rights (ACL and record
  rules included);
- ``tier: "basic"``, ``odoo_rpc: false`` — no API key: the assistant
  answers generically and does not read business data.

Uncheck *Require an Odoo API key for tools* to announce
``odoo_rpc: true`` for everyone (the agent then uses its own service
account, which is a deployment decision, not an Odoo one).

In both cases the agent must never receive more rights than the user:
the API key is the user's own, and the module only reports whether it
exists.

Protocol summary
----------------

+----------------------+-------------------------------------+-----------------------------------+
| Direction            | Endpoint                            | Auth                              |
+======================+=====================================+===================================+
| Odoo -> agent        | ``POST {push_url}``                 | HMAC headers                      |
|                      | (``/odoo/events`` by convention)    |                                   |
+----------------------+-------------------------------------+-----------------------------------+
| agent -> Odoo        | ``POST /ai_agent/reply``            | HMAC headers                      |
+----------------------+-------------------------------------+-----------------------------------+
| agent -> Odoo        | ``POST /ai_agent/poll``             | ``Authorization: Bearer <token>`` |
+----------------------+-------------------------------------+-----------------------------------+
| agent -> Odoo        | ``POST /ai_agent/webhook/<token>``, | token in path                     |
| (legacy)             | ``/ai_agent/push/<token>``          |                                   |
+----------------------+-------------------------------------+-----------------------------------+
| agent -> Odoo        | ``POST /ai_agent/notify/<token>``   | token in path                     |
+----------------------+-------------------------------------+-----------------------------------+

Every JSON answer carries ``status`` in the body (``ok``/``error`` plus
an ``error`` code): the JSON-RPC transport always returns HTTP 200, so
the status must be read from the body.

Answer payload:

.. code:: json

   {"tenant": "...", "delivery_id": "<uuid>", "queue_id": 42, "channel_id": 11,
    "action": "post_message", "body": "the answer", "format": "markdown|html",
    "usage": {"tokens_in": 0, "tokens_out": 0, "ms": 0}}

A repeated ``delivery_id`` is answered with
``{"status": "ok", "duplicate": true}`` and posts nothing: retries are
safe. A reply closes exactly its ``queue_id``, so two conversations in
flight in one channel cannot swallow each other.

Letting the assistant read Odoo as the user
-------------------------------------------

A user can hand their own API key to the assistant, so answers can be
based on records **that user** is allowed to see:

1. The administrator enables **Allow users to connect** on the agent.
2. The user opens **Preferences → Hermes AI** and clicks **Connect
   Hermes**. Odoo creates an API key in that user's own name (scope
   ``rpc``) and leaves it in a one-shot hand-off for the agent.
3. The agent collects it on ``/ai_agent/credentials``, stores it
   encrypted on its side, checks it with a real RPC call, and wipes the
   plaintext in Odoo.
4. **Disconnect** revokes the key immediately; otherwise it expires
   after *Credential validity (days)*.

Nothing is typed by hand and nothing appears in the chat. Because the
key is the user's own, the assistant inherits exactly that user's access
rights and record rules: it cannot read what the user cannot read, and
the key can be revoked from the same screen.

Note: Odoo stores API keys hashed, so a key cannot be read back later.
The hand-off is therefore one-shot: if the agent loses it, the user
reconnects.

Letting the assistant use Odoo tools
------------------------------------

A connected user can also let the assistant *query* Odoo. The default
policy is **Any model the user may read** (``tool_access_mode`` on the
agent): the assistant inherits the user's own API key, so it can read
exactly what that user can read in the interface, and nothing else. Read
methods only (``search_read``, ``read``, ``fields_get``,
``search_count``, ``read_group``); no write is exposed yet.

Two optional restrictions, for customers who want to be stricter than
Odoo's own access rights:

- **Only the Tools list** (``tool_access_mode = whitelist``): the
  assistant may only touch the models listed under **Hermes → Tools**,
  for the groups bound to each record. Each record carries one model,
  one method, a row cap and an optional field list. ``fields_get`` and
  ``search_count`` are implied by a read grant on the same model.
- **Models hidden from the assistant**: a deny list that applies in both
  modes. Its real use is not secrecy but privacy in the channel — an
  answer is posted in Discuss where other members read it, so a customer
  may keep payroll or contracts out of the assistant even though the
  user could open them.

The agent checks every call with Odoo before running it and uses the
user's own key, so a cached tool list or a prompt injection cannot widen
either mode. ``odoo_models`` lets the assistant discover what it may
query instead of guessing.

What the user is looking at
---------------------------

When the assistant lives in Discuss, it has no idea which screen the
user has open — and a support question usually starts with "this
invoice". A small web asset reports the current URL on every navigation
(throttled to one request every few seconds, only when the page actually
changed) to ``/ai_agent/web_context``, which stores one context per
user: model, record id, view type, action and URL.

The context travels with the next message (``view_context``) and the
responder treats it as a **hint**: it may say "you are looking at a sale
order in form view", but it can never widen access, because every read
still runs with the user's own API key. A context older than an hour is
flagged ``stale``, and a cron forgets contexts nobody refreshed for 30
days.

The reference bridge prefixes the message with that context, so the
agent can answer about "this record" without being told which one.

Giving the agent a role: instructions, skills, knowledge
--------------------------------------------------------

An agent record is not only a transport endpoint, it carries the
configuration the responder applies to every conversation:

- **Instructions**: what the agent is for, written by the customer
  administrator.
- **Operator instructions**: owned by whoever runs the responder (safety
  rules, tone, escalation). The responder applies them **after** the
  customer instructions, so a customer edit can never weaken an operator
  rule.
- **Skills**: reusable blocks of instructions plus the tool names they
  expect (Hermes → Skills). Several agents can share one skill.
- **Knowledge**: plain text sources sent as context, capped by
  *Knowledge budget* so a conversation cannot grow unbounded. Nothing is
  indexed in Odoo: the responder does the retrieval, and a glue module
  can fill the body from ``document_page``.
- **Model override**: a provider and a model for this agent
  (``deepseek`` + ``deepseek-v4-pro``). The responder receives both and
  decides how to apply them; the reference bridge passes the model name
  and lets the gateway resolve the provider. **The provider credential
  never leaves the responder**, so an Odoo administrator can choose the
  model without ever seeing the API key.

All of it travels in the poll response under ``agent``, plus the stable
``agent_key`` on every message, so one responder can serve several
agents with different roles.

Files the user sends
--------------------

A message may carry attachments. Each queued message remembers them
(``ai_bridge_agent_message_attachment_rel``) and the payload lists them
with a token-authenticated URL:

.. code:: json

   "attachments": [{"id": 42, "name": "screen.png", "mimetype": "image/png",
                    "size": 81234, "url": "/ai_agent/attachment/<token>/42"}]

The download endpoint only serves files that were queued for **that**
agent, so a leaked URL is useless to another tenant.
``POST /ai_agent/webhook/<token>`` accepts the reverse direction
(``attachments`` with base64), which is how the assistant sends files
back.

The reference responder writes the incoming files under its inbox, tells
the model where they are (with a text preview for text-like files), and
deletes them once the answer is posted. Reading an image also needs a
vision-capable auxiliary model configured on the responder; without one
the assistant knows a file arrived but cannot describe it.

Rendering and attachments
-------------------------

The reply payload tells Odoo how to read the answer, so the assistant is
not forced into plain text:

+---------------------+------------------------------------------------+
| ``format``          | What Odoo does                                 |
+=====================+================================================+
| ``plain`` (default) | escapes, keeps line breaks, turns bare URLs    |
|                     | into links                                     |
+---------------------+------------------------------------------------+
| ``markdown``        | converts tables, lists, fenced code to HTML,   |
|                     | then sanitizes                                 |
+---------------------+------------------------------------------------+
| ``html``            | sanitizes and keeps the markup                 |
+---------------------+------------------------------------------------+

``markdown`` degrades to ``plain`` when python-markdown is not installed
on the server, so the module stays installable without it. Everything is
sanitized whatever the format: a model answer can never inject a script
into Discuss.

A reply may also carry ``attachments``, a list of
``{name, mimetype, b64}`` (5 files, 10 MB total). Odoo stores them as
regular Discuss attachments on the message, so they respect the
channel's access rights and show the usual download link. Path
separators in names are neutralized.

The reference responder only attaches files it finds in its own outbox
directory, and removes them once posted: the assistant cannot exfiltrate
an arbitrary server file by naming it.

Troubleshooting
---------------

- *Queue rows stay pending*: the agent is not polling and push is
  disabled or failing — check ``last_error``/``last_error_date`` on the
  agent, and ``pending_count`` for the queue depth.
- *``dead`` state*: ``max_attempts`` reached. Fix the agent, then use
  **Retry** on the queue rows.
- *Signature rejected*: the agent clock is more than 5 minutes off, or
  the secret does not match the one in Odoo.

Known issues / Roadmap
======================

- Writes: ``create``/``write`` behind an explicit grant and a human
  confirmation in Discuss, on top of the read-only tools already shipped
- Multi-tenant routing: a shared Hermes instance serving several Odoo
  databases, one profile per tenant
- Per-tenant quotas and usage metering (in a child module or the agent,
  never in the transport)
- Support for file attachments and images
- Voice message integration
- Interactive approval buttons in Discuss messages (e.g.
  "Approve/Reject" actions for sensitive operations) — nice to have for
  escalation workflows
- Native Hermes platform adapter (``platform="odoo"``) consuming the
  push envelope directly, without a separate agent script
- WebSocket transport for browsers that cannot reach the agent
