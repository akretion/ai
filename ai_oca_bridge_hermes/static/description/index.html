AI OCA Bridge Hermes

Real-time or polling, pick one

The module exposes two transports for the same conversation:

  • Push (recommended): Odoo signs an event with an HMAC secret and posts it to the gateway the moment a message is committed. Latency is one HTTP call, and no Odoo worker is ever held waiting.
  • Polling (fallback): the gateway calls /hermes/poll and claims the pending messages atomically. Works through any firewall, no inbound route needed on the Odoo side, but costs one request per interval per tenant.

Both transports share one envelope, so a gateway can switch from one to the other without touching the Odoo configuration beyond a checkbox.

Multi-tenant by construction

One Hermes installation can serve many Odoo databases:

  • every database owns a stable tenant_key (an ir.config_parameter, independent from database.uuid) and an environment (prod/staging/dev);
  • the Hermes session key is odoo:<tenant_key>:<environment>:user_<id>, so a staging database restored from production never continues the production conversation;
  • messages are claimed with FOR UPDATE SKIP LOCKED: any number of gateway workers and Odoo HTTP workers can run concurrently without a duplicate delivery;
  • replies are idempotent (delivery_id), and a reply closes exactly the message it answers, not every message of the channel.

Who may talk to the assistant

Access is a group (Use Hermes AI), configurable per gateway. System administrators always keep access so a fresh install stays configurable. Someone outside the allowed groups who addresses the assistant receives a configurable standard answer, posted at most once per cooldown to avoid flooding the channel.

Two capability tiers per user

Not every Odoo user wants to hand an API key to the assistant:

  • a user with an Odoo API key is announced to the gateway as full tier and the gateway may call Odoo on their behalf, with their own access rights;
  • a user without a key is announced as basic tier: generic assistant capabilities only, no Odoo data access.

The module only publishes the fact (capabilities in the envelope) and the policy stays on the gateway side. require_api_key_for_tools decides whether a key is mandatory before announcing odoo_rpc.

What this module deliberately does not do

The module is a transport, published under AGPL-3 in the OCA ai repository. It contains no prompt, no skill, no tool whitelist, no model choice, no tenant-to-customer mapping, no quota and no escalation backend: all of that is product logic and lives in the gateway process, which talks to Odoo only through the documented HTTP envelope. See CONTEXT.md for the boundary and the extension points to use from your own (AGPL) child modules.

Use Cases / Context

Why This Module?

The AI revolution is changing how users interact with software. Odoo users should be able to ask questions, get help, and automate tasks using natural language — directly inside the interface they already use daily.

Architecture Rationale

Two transports, one envelope

Polling was the original design: it works behind firewalls and needs no inbound route on the Odoo side. It stays as the fallback, but it does not scale to many tenants (one request per interval per tenant, a delayed answer, and a gateway that has to hold the conversation state between two polls).

The recommended transport is outbound push: Odoo signs the event and posts it as soon as the transaction is committed (cr.postcommit), so the gateway never sees a message the database could still roll back. A one-minute cron pushes whatever the post-commit hook could not send, which makes a gateway restart or a network glitch invisible to the user.

Both transports carry the same JSON envelope (see USAGE.md), so the gateway only has to implement one parser.

Stateless gateway, persistent session per user

The gateway keeps no conversation state in Odoo: it authenticates with a tenant key, reads the session key from the envelope, and answers with a delivery_id. The Hermes session itself is persistent (session_scope: per user by default, per channel optionally), which is what gives the assistant a memory across messages without storing a transcript in Odoo.

Atomic claiming

/hermes/poll claims messages with a single UPDATE ... FOR UPDATE SKIP LOCKED ... RETURNING. This is what makes several gateway workers and several Odoo HTTP workers safe together, and it removes the previous per-gateway one-second throttle that capped every tenant of a database.

Standalone gateway

scripts/hermes_odoo_gateway.py polls in echo mode or with a Hermes AIAgent. scripts/hermes_push_server.py is the reference push receiver: it verifies the HMAC signature, answers, and is the place to plug the agent call. Neither needs to run inside Odoo’s Python environment.

Extension points

The module is intentionally minimal. Child modules can extend, without forking:

  • hermes.gateway._is_user_allowed(user) — who may talk to the assistant;
  • hermes.gateway._get_capabilities(message) — what the gateway may do for that user (full/basic, odoo_rpc, tool list);
  • hermes.gateway._build_event_payload(message) — enrich the envelope with business context;
  • hermes.gateway._get_session_key(user, channel) — session granularity;
  • hermes.message.queue._get_history(limit) — what the assistant sees of the conversation;
  • discuss.channel._should_queue_for_hermes(message, gateway) — routing rules;
  • hermes_webhook._action_escalate(gateway, data) — escalation backend.

The AGPL boundary (read this before adding private logic)

This module is AGPL-3 and published at OCA. A child Odoo module that inherits it is a derivative work: it must stay AGPL, and if you serve it over the network the AGPL asks you to offer its source to the users. So the private value of the product must not live in an Odoo module:

  • keep in Odoo only the transport, the traceability and the coarse access policy that you are happy to publish;
  • keep prompts, skills, tool whitelists, model/provider choice, tenant registry, quotas, billing and routing intelligence in the gateway process, which talks to Odoo over the documented HTTP envelope;
  • if a private Odoo child module is really needed, accept that it is AGPL too (that is fine for internal, non-distributed deployments, but it is a conscious choice, not an accident).

Escalation Concept

The module includes a minimal escalation hook (_action_escalate) so the AI can signal when human intervention is needed. The base module does not implement any specific escalation backend — child modules can override this hook to create tickets, notify teams, or route to another Hermes instance.

Security Model

  • Webhook tokens are auto-generated, rotatable with a grace period (the previous token stays valid for token_grace_minutes), compared in constant time and never trusted from the URL alone: the recommended endpoints authenticate with an HMAC signature over <timestamp>.<body>;
  • AI users are regular Odoo users with limited permissions;
  • the gateway runs with its own credentials and, per user, with that user’s API key when there is one;
  • queue rows are protected by a multi-company rule and by an own-messages-only rule for non-managers;
  • the Odoo side never executes code sent by the gateway.

Recommended presets

  • Single customer, behind a firewall: push disabled, long poll 20 s, one gateway worker. Nothing has to reach Odoo from outside.
  • Akretion-style shared Hermes: push enabled over HTTPS, HMAC secret per tenant, environment set per database, one gateway worker per tenant queue.
  • Pilot with power users only: allowed groups = a dedicated group, API key required for tools, session scope per user.

Usage

Configuration

  1. Create the AI user: a regular Odoo user, member of no group of its own, linked to an ai.bridge with usage Hermes (this is what makes Discuss treat it as an assistant).
  2. Go to AI Bridge > Hermes > Gateways and create a gateway: name, AI user, environment (prod/staging/dev) and the groups allowed to chat with it. System administrators always keep access.
  3. Copy the webhook token for the polling transport, and the HMAC secret (push_secret) for the push transport. Both are shown to system administrators only.
  4. Optional: restrict the gateway to specific channels, otherwise every channel the AI user belongs to is monitored, and group channels answer only when the assistant is mentioned.

Real-time push (recommended)

In the Realtime push section, check Push enabled and set the gateway URL, e.g. https://hermes.example.com/odoo/events. Odoo then posts every new message after the transaction commits, signed with:

X-Hermes-Tenant:    <tenant_key>
X-Hermes-Timestamp: <unix seconds>
X-Hermes-Delivery:  <uuid>
X-Hermes-Signature: sha256=<hmac_sha256(push_secret, "<timestamp>.<raw body>")>

A one-minute cron retries whatever the post-commit hook could not deliver, so a gateway restart does not lose a message. Leaving push disabled keeps the polling transport in charge.

Polling (fallback)

python scripts/hermes_odoo_gateway.py \
    --odoo-url https://odoo.example.com \
    --webhook-token YOUR_TOKEN \
    --poll-interval 5

Add --use-agent --model ... --provider ... to answer with a Hermes AIAgent instead of echo mode. Set Long poll timeout on the gateway (0-20 s) to hold the request until a message arrives instead of paying a fixed interval.

Reference push receiver

python scripts/hermes_push_server.py \
    --port 8770 \
    --odoo-url https://odoo.example.com \
    --tenant <tenant_key> \
    --secret <push_secret> \
    --mode echo

It verifies the signature, answers /hermes/reply with the same HMAC scheme and is the place to plug the agent call (build_answer).

Access control

Users outside the allowed groups are answered with a standard message (configurable per gateway, Access denied message), posted at most once per denial_cooldown_minutes per channel. Administrators are always allowed.

Two capability tiers

The envelope announces what the gateway may do for the user:

  • tier: "full", odoo_rpc: true — the user owns an Odoo API key, so the gateway can call Odoo with that user’s rights (ACL and record rules included);
  • tier: "basic", odoo_rpc: false — no API key: the assistant answers generically and does not read business data.

Uncheck Require an Odoo API key for tools to announce odoo_rpc: true for everyone (the gateway then uses its own service account, which is a deployment decision, not an Odoo one).

In both cases the gateway must never receive more rights than the user: the API key is the user’s own, and the module only reports whether it exists.

Protocol summary

Direction Endpoint Auth
Odoo -> gateway POST {push_url} (/odoo/events by convention) HMAC headers
gateway -> Odoo POST /hermes/reply HMAC headers
gateway -> Odoo POST /hermes/poll Authorization: Bearer <token>
gateway -> Odoo (legacy) POST /hermes/webhook/<token>, /hermes/push/<token> token in path
gateway -> Odoo POST /hermes/notify/<token> token in path

Every JSON answer carries status in the body (ok/error plus an error code): the JSON-RPC transport always returns HTTP 200, so the status must be read from the body.

Answer payload:

{"tenant": "...", "delivery_id": "<uuid>", "queue_id": 42, "channel_id": 11,
 "action": "post_message", "body": "the answer", "format": "markdown|html",
 "usage": {"tokens_in": 0, "tokens_out": 0, "ms": 0}}

A repeated delivery_id is answered with {"status": "ok", "duplicate": true} and posts nothing: retries are safe. A reply closes exactly its queue_id, so two conversations in flight in one channel cannot swallow each other.

Letting the assistant read Odoo as the user

A user can hand their own API key to the assistant, so answers can be based on records that user is allowed to see:

  1. The administrator enables Allow users to connect on the gateway.
  2. The user opens Preferences → Hermes AI and clicks Connect Hermes. Odoo creates an API key in that user’s own name (scope rpc) and leaves it in a one-shot hand-off for the gateway.
  3. The gateway collects it on /hermes/credentials, stores it encrypted on its side, checks it with a real RPC call, and wipes the plaintext in Odoo.
  4. Disconnect revokes the key immediately; otherwise it expires after Credential validity (days).

Nothing is typed by hand and nothing appears in the chat. Because the key is the user’s own, the assistant inherits exactly that user’s access rights and record rules: it cannot read what the user cannot read, and the key can be revoked from the same screen.

Note: Odoo stores API keys hashed, so a key cannot be read back later. The hand-off is therefore one-shot: if the gateway loses it, the user reconnects.

Letting the assistant use Odoo tools

A connected user can also let the assistant query Odoo through a whitelist the customer controls: Hermes → Tools.

Each record opens one model with one read method (search_read, read, fields_get, read_group), for the groups you choose, with a row cap and an optional field list. Two defaults ship for every internal user: partners and products, read only. To give a power user more, add a record for the model they need and put them in a dedicated group: nothing else changes, and the regular users never see it.

fields_get and search_count are implied by any read grant on the same model: the assistant can inspect the schema it may read and count rows without paging through them (a “how many invoices this month” answer costs one call instead of forty).

The gateway checks every call against these records before running it, with the user’s own API key: a stale tool list or a prompt injection cannot widen what the whitelist allows, and writes are not exposed at all yet.

Troubleshooting

  • Queue rows stay pending: the gateway is not polling and push is disabled or failing — check last_error/last_error_date on the gateway, and pending_count for the queue depth.
  • ``dead`` state: max_attempts reached. Fix the gateway, then use Retry on the queue rows.
  • Signature rejected: the gateway clock is more than 5 minutes off, or the secret does not match the one in Odoo.

Known issues / Roadmap

  • Writes: create/write behind an explicit grant and a human confirmation in Discuss, on top of the read-only tools already shipped
  • Multi-tenant routing: a shared Hermes instance serving several Odoo databases, one profile per tenant
  • Per-tenant quotas and usage metering (in a child module or the gateway, never in the transport)
  • Support for file attachments and images
  • Voice message integration
  • Interactive approval buttons in Discuss messages (e.g. “Approve/Reject” actions for sensitive operations) — nice to have for escalation workflows
  • Native Hermes platform adapter (platform="odoo") consuming the push envelope directly, without a separate gateway script
  • WebSocket transport for browsers that cannot reach the gateway
