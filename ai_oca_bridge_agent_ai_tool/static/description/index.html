AI Bridge Agent - AI Tool

The bridge agent module keeps the transport and the data policy. This module adds the other half of the tool story: declared operations.

OCA ai.tool records describe one curated operation with an input and output schema — a Python function today, a server action once ai_tool_server_action lands. Here an administrator assigns those tools to a bridge agent, and a user talking to that agent can run them.

The two words stay apart:

  • a grant (ai.bridge.agent.grant) bounds which data the assistant may read with the user’s own key;
  • a tool (ai.tool) declares an operation the assistant may perform.

Tools are assigned explicitly, one by one: a tool that mutates records must never reach an agent by accident.

Everything runs with the rights of the user who is chatting. The tool is executed in that user’s environment, never the agent’s AI user and never sudo, so Odoo ACLs and record rules apply exactly as if the user had clicked in the interface.

A tool is reachable only when it is assigned to the agent, and only for users who may read the model it acts on; a record tool also checks the record itself. readonly marks the tools that only read, and an agent in Only read-only tools mode refuses the others. The whole trust model is described in the Security model section of the ai_oca_bridge_agent module’s USAGE.md.

Usage

Assign tools to an agent

Tools reach an agent two ways, and both are explicit:

  • directly, on the agent form, Tools tab: add the ai.tool records this agent may run;
  • through a skill: a skill carries its tools like a bundle, so putting “Search Database” on an agent brings its tools with it, exactly as a reusable prompt pack should. A tool listed both ways is offered once.

An agent with no tool and no skill runs none. Only read-only tools refuses every tool not flagged readonly, which is how an assistant stays useful without being able to change a record.

A tool is offered only when the user talking to the agent may read the model the tool acts on. The check is a courtesy: the boundary is the user’s own access rights, applied when the tool runs.

Endpoints the responder calls

Both are authenticated with the agent token (Authorization: Bearer <token>).

POST /ai_agent/tools/declared
{"user_id": 42}
-> {"status": "ok", "tools": [{"name": ..., "description": ...,
                               "inputSchema": {...}, "outputSchema": {...}}]}

POST /ai_agent/tools/call
{"user_id": 42, "tool": "get_date", "arguments": {},
 "record_model": "res.partner", "record_id": 7}
-> {"status": "ok", "result": {...}}

record_model and record_id are only needed by tools that work on a record; record_model is the model of that record for a generic_model tool, whose own model is the one holding the function.

Refusals are explicit: unknown_user, user_not_allowed, missing_tool, tool_not_assigned, tool_not_readonly, bad_arguments, tool_failed with a short message. Each definition carries readonly and kind so the responder can present mutating tools differently.

Server actions as tools

Install ai_tool_server_action (once merged, or the review branch) and the same tab offers server-action tools with no extra configuration here: they are ai.tool records like the others, and they run with the user’s rights.
